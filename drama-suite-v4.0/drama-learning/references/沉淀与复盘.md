# 沉淀与复盘

## 规律放在哪里

学到的规律按内容写进项目资料库的 `patterns/` 下对应的文件。文件结构见 [patterns 文件结构](../templates/patterns文件结构.md)。

| 内容 | 文件 | 读取它的模块 |
|---|---|---|
| 剧本、结构、钩子、对白 | `patterns/script.md` | drama-script |
| 角色造型、场景美术、声线 | `patterns/assets.md` | drama-assets |
| 色彩、光线、镜头、构图、表演、生成写法、剪辑、声音 | `patterns/visual.md` | drama-direction、drama-storyboard、drama-production、drama-editing |
| 封面、标题、文案 | `patterns/materials.md` | drama-materials |

一个参考涉及多个方面时，分别写进对应的文件，用同一个参考编号。

## 三个层级

| 层级 | 写在哪里 | 什么时候 |
|---|---|---|
| 项目规律 | 项目资料库的 `patterns/` | 用户说入库、锁定、以后这样做 |
| 题材或形态档案 | 项目的 `profiles/`；用户同意推广时，写进套组的 `profiles/` | 同一条规律在这个题材或形态的两个以上项目里都有效，且用户同意推广 |
| 通用内核 | 套组各模块的 references | 用户明确要求修改 skill |

**往上一层推广时检查：**

- 去掉项目特有的内容：人物、故事、具体的数值、曲目。
- 写清适用的条件和不适用的情况。
- 和这一层已有的规则不冲突；冲突时写清替代关系，旧规则保留在 CHANGELOG 里。

## 写入规律

每条规律包括：

- 编号和来源（参考卡编号或复盘记录）
- 触发条件：什么情况下用
- 操作：具体做什么
- 预期效果
- 不适用的情况
- 证据与未核验的部分
- 状态：候选、已采用、已停用
- 采用的授权来源和日期

写入后更新资料库的更新日志，并告诉用户哪些模块会受影响。

沉淀改变的是后续执行时读取的指导，不是训练模型，也不会自动重做已经完成的成片。

## 每集复盘

每集终检通过后做一次，用 [复盘记录模板](../templates/复盘记录模板.md)。材料来自：

- 各模块的评审记录，尤其是最弱的三处
- 审片记录里的问题和诊断
- 返修的次数和原因
- 预演关卡和终检发现的问题
- 用户的反馈
- 发布后的数据（有的话）

**回答四个问题：**

1. **什么做对了？** 哪些决定效果好，值得下一集继续。
2. **什么做错了？** 问题出在哪一个环节。追到根源：成片的问题，常常来自分镜，分镜的问题，常常来自剧本。
3. **规则有用吗？** 套组和档案里的哪些规则帮上了忙，哪些没起作用，哪些反而碍事。
4. **下一集改什么？** 具体的、可执行的改动。

**输出：**

- 候选规律，交用户决定是否入库。
- 模型适配卡的更新（已知弱点、有效的写法）。
- 对档案或套组的修改建议，单独列出，由用户决定。

复盘只记事实和建议，不自行修改已确认的规则。单次的偏好不升级为长期规则。

## 迁移旧的 skill 或规则

学习一套已有的 skill（包括旧版的项目私有规则）时：

1. 连同它实际引用的文件一起读，按模块审读。
2. 建立对应表：每条原规则，去向哪里。
   - 通用的执行规则：保留进对应模块。
   - 项目的参数：改为项目配置项，保留检查机制。
   - 世界观、人物、具体剧情：留在原项目。
3. 不能以通用化为理由删掉有用的制作规则：原文映射、表演栏、资产拆解、提交核对、制作包等。
4. 迁移清单写明：每条的去向、参数化的说明、没有覆盖到的内容。没读到的文件不能声称已迁移。
